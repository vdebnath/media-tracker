1. N-tier architecture is a design system where code is seperated into disctinct tiers (seperate projects for this repo). These seperate tiers are assigned unique responsibilities and can only communicate with tiers directly next to them in the heiarchy. We use this system to help organize code & responsibilities (code structure & helps knowing where to look when trying to find a specific part), make testing code a lot easier (helps with making tests specific for each tier, also can use mock databases so no connection is needed to a real one), help with maintaince and future enhancements (can implement new features and have greater certanty it'll work with the tests), and to set an ordered structure in which to write code (gives standard in which to add code/fix existing parts). 

2. For this project we have the front end Angular Typescript section, not part of C# but can be seen as part of the architecture. Next comes the API/Controller tier. This part talks with the frontend as well as the Services tier and is responsible for managing http requests and responses. Next comes the services layer, which talks with the API/Controller & Data layers. The services tier manages data manipulation and transformations and any modifications based on buisiness logic. The last C# tier is the Data layer which talks with the database and Services tier in order to read & write from and to the database (sql in this project). 

3. The controller should not talk directly with the databse in order to maintain the seperation of functionality rule. Introducing database calls in the controller tier can lead to increased code complexity as well as harder debugging sessions when errors would arise. Main issues aries in having to connect with an actual database, increasing testing times from latency. Other issues such as accidentily updating existing records in the real DB can also occur, which can be bad for end users. Using a services tier that uses a DB interface helps avoid these issues. 

4. Dependancy injection is the practice of providing classes with external dependancies instead of the class needing to make objects for them. This reduces need for overhaul if methods being depended on change in how they are used. Most common form is constructor DI where the dependency is added to the object during instansiation, allowing users to view what all the class needs. Interfaces are commonly used in DI as they allow for different implementatons of methods without needing to change the class the dependency is being used in. Testing gets a major benefit from DI as users are able to inject different variations of interfaces to suite the tests, be it a mock or actual DB connection.
